🎓 From zero to slopstopper · lesson 13

Core Web Vitals

Goal. Run Lighthouse against the demo, read the budget it enforces, add one blocking script, and watch the numbers move.

Why this check

Performance slop never looks like a performance change. It is a 400 KB web font added for one heading, an image without dimensions, an analytics snippet pasted into <head> because that is where the vendor's instructions put it. Each is one line in a PR. Nobody notices until the page feels slow on a phone, and by then there are a dozen such lines and no way to tell which one did it.

reliability:cwv turns the feeling into a number with a threshold. It runs Lighthouse three times against each URL and asserts on the metrics Google calls Core Web Vitals: Largest Contentful Paint (how long until the main content is on screen), Total Blocking Time (how long the main thread is busy and cannot respond), and Cumulative Layout Shift (how much the page jumps around while loading), plus the overall performance and SEO scores. Each assertion is judged on the best of the three runs, so one slow run on a noisy CI machine does not fail the build.

The budgets are deliberately loose: a static site clears them easily, and a budget that fires on runner noise is worse than none. They live in Lighthouse's own config, bundled in the wheel, with a dev set for local and pull-request runs and a stricter prod set for the live site. Exit 0 is every assertion within budget, 1 is a budget missed, 2 is Lighthouse could not run: no Chrome, no npx, the URL unreachable.

You will need

  • The demo repo from the syllabus, with the CLI on PATH.
  • node, and in the demo npm install (its package.json lists Lighthouse CI alongside Playwright).
  • A Chrome or Chromium that Lighthouse can launch. It finds an installed Chrome on its own; CHROME_PATH points it at another, such as the Chromium Playwright installed.

Steps

1. Serve the demo and see it green

Three Lighthouse runs take about a minute.

mkdir -p scratch
PORT=8099 slopstopper serve >/dev/null 2>&1 & echo $! > scratch/serve.pid
sleep 2
slopstopper run reliability:cwv -- http://localhost:8099

2. Read the budget

sed -n '/| Metric/,/CLS/p' .ss/reports/cwv/cwv-report.md
| Metric | Threshold | Status |
|--------|-----------|--------|
| Performance score | ≥ 70 | ✅ 100/100 |
| LCP | ≤ 4 s | ✅ 901 ms |
| TBT | ≤ 600 ms | ✅ 0 ms |
| CLS | ≤ 0.25 | ✅ 0.000 |

The status page paints its main content in under a second, blocks the main thread for no time at all, and nothing shifts. The full Lighthouse HTML reports, one per run, are under .ss/reports/cwv/lighthouse/, and CI uploads them as an artifact.

3. Add one blocking script

A script in <head> without defer runs before the browser renders anything below it. This one does nothing but spin for a second and a half, which is what a badly written tag manager does while it decides what to load.

printf 'const until = Date.now() + 1500;\nwhile (Date.now() < until) {}\n' > app/slow.js
sed -i.bak 's|<link rel="stylesheet" href="style.css">|<script src="slow.js"></script>\n  <link rel="stylesheet" href="style.css">|' app/index.html && rm app/index.html.bak
slopstopper run reliability:cwv -- http://localhost:8099
  ✘  largest-contentful-paint failure for maxNumericValue assertion
       Largest Contentful Paint
       https://developer.chrome.com/docs/lighthouse/performance/lighthouse-largest-contentful-paint/
        expected: <=4000
           found: 6900.44
      all values: 6905.4663, 6900.44, 6903.2413
Assertion failed. Exiting with status code 1.

Lighthouse names the audit, links its explanation, and shows all three runs so you can see the miss is not noise. The report table says the same in one line each:

sed -n '/| Metric/,/CLS/p' .ss/reports/cwv/cwv-report.md
| Metric | Threshold | Status |
|--------|-----------|--------|
| Performance score | ≥ 70 | ❌ 60/100 |
| LCP | ≤ 4 s | ❌ 6903 ms |
| TBT | ≤ 600 ms | ✅ 0 ms |
| CLS | ≤ 0.25 | ✅ 0.000 |

One script, and the main content takes seven times as long to appear. TBT did not move at all, because the spin happened before anything painted; it is LCP that paid for it. That is the point of measuring more than one thing: the same change shows up in a different metric depending on where in the load it lands.

4. Fix it

The real fix for a script like this is defer, or loading it after the content, or not loading it at all. Here it was scratch, so remove it and run again.

git checkout app/index.html
rm app/slow.js
slopstopper run reliability:cwv -- http://localhost:8099 >/dev/null 2>&1
sed -n '/| Metric/,/CLS/p' .ss/reports/cwv/cwv-report.md
| Metric | Threshold | Status |
|--------|-----------|--------|
| Performance score | ≥ 70 | ✅ 100/100 |
| LCP | ≤ 4 s | ✅ 901 ms |
| TBT | ≤ 600 ms | ✅ 0 ms |
| CLS | ≤ 0.25 | ✅ 0.000 |

5. Know the knobs

The budgets are in lighthouserc.json (dev) and lighthouserc.prod.json (prod) inside the wheel. slopstopper templates eject lighthouserc.json drops an editable copy into .ss/, which the check prefers. --prod selects the stricter set, which the daily run against production and the post-deploy trigger use. Nothing leaves your machine by default: publishing a report to Lighthouse's public storage is opt-in through reliability.cwv.public_report, and the report links it when on.

Checkpoint

kill "$(cat scratch/serve.pid)"
rm -r scratch
grep 'Core Web Vitals' .ss/reports/cwv/cwv-report.md
## 🚦 Core Web Vitals ✅ PASSED

Exercise

Tighten one budget until the demo, unchanged, fails it. Then put the budget back.

Solution

Eject the dev config and lower the LCP budget below what the page achieves:

slopstopper templates eject lighthouserc.json
sed -i.bak 's/"maxNumericValue": 4000/"maxNumericValue": 500/' .ss/lighthouserc.json && rm .ss/lighthouserc.json.bak
slopstopper run reliability:cwv -- http://localhost:8099
rm .ss/lighthouserc.json

LCP at around 900 ms now fails a 500 ms budget. The exercise is the honest way to raise the bar: tighten one budget to just above what you have measured for a few weeks, then another, rather than guessing at the numbers on day one.
