Profiles and tailoring

Goal. Switch a repo between the ui, api and library profiles, keep one check a profile drops, and know where the CLI pin lives and how it moves.

Why this lesson

A check that cannot apply is noise, and noise is how gates get ignored. The nine browser checks assume HTML, a DOM and a public web surface; on an API they do not quietly no-op, they build, serve and audit nothing and go red, and on a library there is nothing to serve at all. A profile is a named preset for workflows.disabled that says which workflows a repo of that shape should not carry. It only ever subtracts, and workflows.enabled takes an individual check back out of the profile's set, so an API that does serve a docs site can keep the broken-links check.

The design has two rules worth knowing. The config is the home, not the flag: install.sh --profile api writes profile: api into .slopstopper.yml, and everything downstream (doctor, the installer, the badges, the deploy trigger) reads the same resolved set from the one mapping in profiles.json. And detection suggests, never applies: profile detect reads the repo's contents and prints a suggestion, because a wrong silent pick, with checks quietly off, is worse than the default superset, with checks visibly red.

The other thing an adopter tailors is the CLI version, which is pinned per repo in mise.toml so a breaking upstream release cannot reach a repo until someone moves the pin.

You will need

The demo repo from the syllabus, with the CLI on PATH.

Steps

1. See what this repo resolves to, and why

Install the suite into the demo first (lesson 1), quietly, so the profile has workflows to act on.

slopstopper --quiet install --no-topic --no-hooks --no-skills
slopstopper profile show
  Profile: ui  (from .slopstopper.yml)
      A web UI: a site or app that serves HTML to a browser.

  Disabled workflows (4):
    · ss-hygiene-openapi-check.yml               (profile, no API detected)
    · ss-reliability-api-health-check.yml        (profile, no API detected)
    · ss-reliability-api-latency-check.yml       (profile, no API detected)
    · ss-security-api-headers-check.yml          (profile, no API detected)

Every check applies to a site, except the four API checks from lesson 16, which the ui profile holds back until the repo shows an API: a spec, a server framework or an api.* key. Each line says why it is off.

2. Ask for a suggestion

slopstopper profile detect
  Suggested profile: ui  (found app/index.html)
  Active profile:    ui (already a match, nothing to do).

The installer prints the same suggestion when it differs from the active profile, and still does not change anything.

3. Read the whole mapping

slopstopper profile list

      …
      holds back 4 workflow(s) until the repo shows an API:

        · ss-hygiene-openapi-check.yml

        · ss-reliability-smoke-tests.yml
        · ss-reliability-e2e-check.yml
        …

  library
      A library, CLI or package with no deployed surface of any kind.
      …
      disables 16 workflow(s):

4. Switch the repo to the API profile

The installer does this with --profile api; the key it writes is the whole mechanism, so write it yourself.

sed -i.bak 's/^profile: ui$/profile: api/' .slopstopper.yml && rm .slopstopper.yml.bak
slopstopper profile show
  Profile: api  (from .slopstopper.yml)
      An HTTP API: JSON/gRPC endpoints with no browser-rendered surface.

  Disabled workflows (10):
    · ss-hygiene-privacy-check.yml               (profile)
    · ss-reliability-accessibility-check.yml     (profile)
    · ss-reliability-broken-links-check.yml      (profile)
    · ss-reliability-core-web-vitals.yml         (profile)
    · ss-reliability-e2e-check.yml               (profile)
    · ss-reliability-llms-txt-check.yml          (profile)
    · ss-reliability-robots-txt-check.yml        (profile)
    · ss-reliability-seo-check.yml               (profile)
    · ss-reliability-sitemap-check.yml           (profile)
    · ss-reliability-smoke-tests.yml             (profile)

The four API checks are back, because the api profile keeps them, and the nine browser checks and the privacy statement check (a page nobody serves) are gone from the resolved set. The files are still on disk until the installer runs again, which is what install.sh does on a refresh:

slopstopper install --no-topic --no-hooks --no-skills | grep 'not installed for this repo shape'
ls .github/workflows | wc -l
ℹ️  profile 'api': 10 workflow(s) not installed for this repo shape (10 removed from a previous install)
21

Ten removed, four API ones added: twenty-one workflows where lesson 1 had twenty-seven. The deploy trigger stops dispatching the nine too; slopstopper profile disabled prints the resolved set one per line, which is what both of them read.

5. Keep one of them

An API that serves its own docs pages still wants the link check.

python3 - <<'PY'
import pathlib
path = pathlib.Path(".slopstopper.yml")
text = path.read_text()
path.write_text(text.replace("  enabled: []", "  enabled: [ss-reliability-broken-links-check.yml]"))
PY
slopstopper profile show
  Profile: api  (from .slopstopper.yml)
      An HTTP API: JSON/gRPC endpoints with no browser-rendered surface.

  Disabled workflows (9):
    · ss-hygiene-privacy-check.yml               (profile)
    …
    · ss-reliability-smoke-tests.yml             (profile)

  Re-enabled by workflows.enabled despite the profile:
    · ss-reliability-broken-links-check.yml

The arithmetic is one line in the CLI: the profile's set, minus workflows.enabled, plus workflows.disabled. Put the config back:

git checkout .slopstopper.yml

6. Find the pin

grep -A3 '^\[tools\]' mise.toml
[tools]
"node" = "20"
"task" = "3"
"pipx:slopstopper-cli" = "<this CLI's version>"

That third line is what both a laptop and CI install, per directory, so the active slopstopper always matches the repo you are in. The installer seeded it with its own version because the demo had none; a plain install.sh re-run never bumps it, the bootstrap prints a nudge when it is behind PyPI, and install.sh --upgrade-cli (or --cli-version X.Y.Z) is the one command that moves it, by wrapping mise use. The suite a refresh writes is the pinned version's, so a new check arrives with the pin and never before it.

Checkpoint

slopstopper profile show | grep 'Profile: ui'
  Profile: ui  (from .slopstopper.yml)

Put the demo back:

git checkout .gitignore package.json
git clean -fdq

Exercise

How many workflows does the library profile drop, and which hygiene checks are among them?

Solution 
slopstopper profile expand library | wc -l
slopstopper profile expand library | grep hygiene

Sixteen: the nine browser checks, the privacy statement, DAST, CSP exceptions and the four API checks. Three are hygiene checks: CSP exceptions and the privacy statement, which read headers and a page nothing serves, and ss-hygiene-openapi-check.yml, because drift means the spec against the live API it documents. What remains for a library is the static-analysis layer: complexity, the docs checks, secrets, SAST and dependencies, which is the whole of what applies to code nothing serves.
