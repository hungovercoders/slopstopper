🎓 From zero to slopstopper · lesson 10

Dynamic scanning

Goal. Serve the demo, run OWASP ZAP against it, read a baseline report, see what the gate accepts and why, and accept one finding with a reason.

Why this check

Everything before this lesson read the source. security:dast tests the running thing. A header the host strips on the way out, a redirect that leaks the path it came from, a page that caches when it should not, a policy that is tighter in the config file than in the response: none of that is visible in a diff, because all of it is about what a client gets back. This is the one check whose findings a reviewer could not have seen, however carefully they read.

The tool is OWASP ZAP, run from its official Docker image so the CLI ships none of it. The check runs ZAP's baseline scan: it spiders the site from the URL you give it and runs the passive rules over every response, which is the cheap version of dynamic testing and the right one for a pull request. A full active scan sends attack payloads and takes an hour; that is a scheduled job against production, not a PR gate. Each alert carries a risk (High, Medium, Low, Informational), a plugin id, and the URLs it was seen on.

Then the gate decides. Medium and High block, with two narrow exceptions. A CSP finding on a path documented in docs/security/CSP_EXCEPTIONS.md (lesson 9's ledger) is accepted, because the relaxation was reviewed and the ledger says why. And an alert .zap/rules.tsv marks IGNORE, with a reason, is accepted. The report lists what was accepted and names the entry that accepted it, so nothing is quietly swallowed. Exit 0 is no blocking alert left, 1 is at least one, and 2 is Docker missing, nothing listening at a localhost target, or ZAP exiting without a report.

You will need

  • The demo repo from the syllabus, with the CLI on PATH, and node for slopstopper serve.
  • Docker, running. slopstopper doctor says whether it is on PATH; the first scan pulls the ZAP image (about a gigabyte), so it needs the network once.
docker --version

Steps

1. Relax one page, and write it down

The demo's policy is strict enough that ZAP's passive rules find nothing above Low on it, so this lesson makes the relaxation that lesson 9 only documented a little wider: the history page's chart sets inline styles, so style-src admits 'unsafe-inline' there. Both halves at once, the header and the ledger entry, so the drift check stays green.

python3 - <<'PY'
import pathlib
p = pathlib.Path('app/_headers'); text = p.read_text()
head, block = text.split('/history.html\n', 1)
block = block.replace("style-src 'self';", "style-src 'self' 'unsafe-inline';", 1)
p.write_text(head + '/history.html\n' + block)
doc = pathlib.Path('docs/security/CSP_EXCEPTIONS.md'); t = doc.read_text()
entry = '''### `/history.html`

- **Origin allowed:** `https://charts.example.com`
- **Directives added:** `img-src https://charts.example.com`, `style-src 'unsafe-inline'`
- **Loader SRI:** `n/a`
- **Why:** the uptime chart is rendered by the charts service and sets inline styles on its container
- **Approved by:** nobody yet
- **Data leaving site:** visitor IP and User-Agent when the chart image is fetched
- **Refresh policy:** n/a
'''
doc.write_text(t.replace('None yet: every path serves the baseline policy.\n', entry, 1))
PY
slopstopper run hygiene:csp-exceptions | tail -1
✅ No drift detected.

2. Serve the demo and scan it

The site is served on a port of its own, tracked by a pid file so a later step can stop it. The server reads app/_headers when it starts, which is why the relaxation came first. ZAP runs in a container, so the check rewrites localhost to the address the container can reach the host on (host.docker.internal on macOS, the bridge gateway 172.17.0.1 everywhere else) and tells you.

mkdir -p scratch
PORT=8099 slopstopper serve >/dev/null 2>&1 & echo $! > scratch/serve.pid
sleep 2

## 🔵 Low Risk Alerts

The report opens with the accepted findings and the entry behind each, then the counts by risk, then a table per level. The Lows are the cross-origin isolation and permissions-policy headers the demo's host does not send; Low never blocks, so they are there to be read, not fixed today. The JSON beside it has every instance and ZAP's alertRef (10055-6), which is the id you will use in step 5.

4. Take the ledger away

The entry is what made the Medium acceptable. Remove it and the same scan is red.

git checkout docs/security/CSP_EXCEPTIONS.md
slopstopper run security:dast -- http://localhost:8099
⚠️  Found 1 high/medium alert(s) (total 6)
🕷️  DAST gate
   blocking alerts (riskcode >= 2): 1
   swallowed (rules.tsv IGNORE or documented CSP exceptions): 0
❌ 1 blocking finding(s). See .ss/reports/dast/dast-report.md.

Same site, same six alerts, one blocking; the report's Medium table names it. Nothing about the response changed; what changed is that nobody has said why it is acceptable. The gate blocks on a Medium until someone does, in a place a reviewer reads.

5. Accept it with a reason, the other way

For a finding that is not a CSP relaxation on one path (a header a static host cannot send, a rule that misreads a framework), the ledger is the wrong instrument. .zap/rules.tsv is the right one: one line per alert, tab-separated, with the reason as the third field.

mkdir -p .zap
printf '10055-6\tIGNORE\t# inline styles on /history.html: the chart container sets them; the page allows nothing else\n' > .zap/rules.tsv
slopstopper run security:dast -- http://localhost:8099
🕷️  DAST gate
   blocking alerts (riskcode >= 2): 0
   swallowed (rules.tsv IGNORE or documented CSP exceptions): 1
   🛡 /history.html: alert=10055-6 riskcode=2 'CSP: style-src unsafe-inline' ← .zap/rules.tsv entry `10055-6`
✅ No blocking findings.

Green again, and the gate names the line that did it. Two things about the id. 10055-6 is the alert ref: plugin 10055 is ZAP's whole CSP scanner and raises several unrelated alerts, so ignoring 10055 would also hide a missing frame-ancestors; the ref accepts exactly the inline-styles alert and nothing else. And the reason is not optional: the file is read in review, and "IGNORE" with no # why is the quiet relaxation this course exists to stop.

6. Put the demo back

Remove the rule, restore the headers, and stop the server: it read the relaxed headers when it started, so the clean run in the checkpoint needs a fresh one.

rm -rf .zap
git checkout app/_headers
kill "$(cat scratch/serve.pid)"

Checkpoint

PORT=8099 slopstopper serve >/dev/null 2>&1 & echo $! > scratch/serve.pid
sleep 2
slopstopper run security:dast -- http://localhost:8099 2>&1 | grep -E 'Found|No blocking'
kill "$(cat scratch/serve.pid)"
rm -rf scratch
ℹ️  Found 4 alert(s), but none are high/medium
✅ No blocking findings.

The demo as it shipped: four Lows, nothing to accept, server stopped, pid file gone.

Exercise

Point the scan at a live site instead of the local one, and explain the difference in what ZAP sees.

Solution 
slopstopper run security:dast -- https://slopstopper.dev

No 📍 line, because there is nothing to rewrite. The response headers now come from the host's edge rather than from slopstopper serve reading a file, so this is the run that would catch a header the edge strips or adds. That is why the suite scans production after each deploy and daily, and why a local build is enough for a pull request: the two runs answer different questions.
