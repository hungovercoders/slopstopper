Dependencies and licences

Goal. Find the pinned package in the demo with a known CVE, read the report's "Fixed In" column, take the fix, and see where the licence gates sit.

Why this check

security:vulnerability:all stops the slop you did not write: a dependency with a published vulnerability. It arrives in ordinary ways. An agent pins the version it remembers, which is the version from its training data and a year or more old. A requirements file is copied from another project along with its pins. A lock file is regenerated and nobody reads the diff. None of these are mistakes in your code, and no review of your code finds them, because the vulnerable lines are in a package you never open. The only way to know is to look every dependency up against the list of CVEs, and the only way to keep knowing is to do it on every pull request and again on every push to main, because the list grows after your code stops changing.

The tool is Trivy, which scans the filesystem for every dependency manifest and lock file it knows (npm, pip, Go, Cargo, Maven and the rest), resolves each package to a version, and matches them against a vulnerability database it downloads and caches for a day. The check subprocess-invokes it with node_modules and .git skipped, writes the report, and gates on severity: CRITICAL and HIGH exit 1, MEDIUM and LOW are reported and exit 0. That threshold is in the check, not the workflow, so the local run and CI agree. Exit 2 is Trivy missing or its database download failing, because a scan that never finished must not read as clean.

Two companion checks cover licences. The dependency review runs only in CI: it is GitHub's own dependency-review-action on the pull request's manifest diff, so it sees only what the PR adds, and fails a new dependency under a licence outside the allowlist in .github/dependency-review-config.yml. security:licences applies the same allowlist to the whole resolved tree, locally and in CI, so a transitive package under a denied licence cannot sit unseen. Neither gates on a build tool's own dependencies, which is Dependabot's job; the vulnerability doc has the table.

You will need

  • The demo repo from the syllabus, with the CLI on PATH.
  • trivy on PATH. brew install trivy, or a release binary from github.com/aquasecurity/trivy; the suite's own workflow installs it from the Trivy apt repository and this course's CI does the same. The first run downloads the vulnerability database, which takes a minute.
trivy --version | head -1
Version: 0.74.0

Steps

1. See it red

One manifest found, and it is red. The demo's script needs one package, and whoever wrote the requirements file pinned the version they remembered. It is from 2018.

cat scripts/requirements.txt
requests==2.19.1

One line, five findings, none of them in anything you can read in this repo.

The column that matters is Fixed In. Every row names the first version without the hole, so the report is its own fix list: the HIGH needs 2.20.0, and the newest MEDIUM needs 2.33.0. The dates in the CVE ids tell the other story, which is that a pin that was clean in 2018 has had a finding added to it roughly every year since. A dependency you never touch still changes.

3. Take the fix the gate needs

printf 'requests==2.20.0\n' > scripts/requirements.txt
slopstopper run security:vulnerability:all 2>/dev/null
🔍 Scanning dependencies for vulnerabilities…
ℹ️  Found 4 vulnerability(ies), none CRITICAL/HIGH

📁 Reports saved to: .ss/reports/vulnerability-all/
   • vulnerability-all-report.md

Trivy's log lines go to stderr, so dropping that stream leaves the check's own verdict and keeps its exit code, which a pipe into grep would replace. Green, and honest about it: four findings remain, reported and not blocking. The threshold is where it is because a MEDIUM is usually "needs a specific setup to exploit" and blocking on it would make the gate something people route around, which lesson 19 has more to say about. It is still listed, so a reviewer who reads the comment sees it.

4. Then take the fix you want

printf 'requests==2.33.0\n' > scripts/requirements.txt
slopstopper run security:vulnerability:all 2>/dev/null
grep 'No vulnerabilities detected' .ss/reports/vulnerability-all/vulnerability-all-report.md
🔍 Scanning dependencies for vulnerabilities…
✅ No vulnerabilities detected

📁 Reports saved to: .ss/reports/vulnerability-all/
   • vulnerability-all-report.md
No vulnerabilities detected.

The grep is the assertion: exit 0 only says nothing blocking was found, so a clean report is the thing to check for. 2.33.0 is the current release as this lesson was written. When a later one carries a CVE, the harness that checks this course goes red on this block, which is the lesson in miniature: the pin did not change, the world did.

5. Put the demo back

git checkout scripts/requirements.txt

6. When local and CI disagree

This is the one check where they legitimately can. Trivy caches its database for a day, and CI starts cold and pulls the newest one, so a CVE published this morning fails the PR and not your laptop. trivy clean --vuln-db then a rerun reproduces CI; the binary version in the workflow's "Install Trivy" step is the other thing to compare. Treat CI as the verdict.

Checkpoint

slopstopper run security:vulnerability:all >/dev/null 2>&1; echo "exit $?"
exit 1

Red again, with the demo as it shipped, and the fix is a version number the report hands you.

Exercise

The licence allowlist is a file install.sh seeds into every repo. Seed one into the demo by hand, with the GPL family left out, and run the licence inventory against the demo's one dependency.

Solution 
mkdir -p .github
printf 'allow-licenses:\n  - MIT\n  - Apache-2.0\n  - BSD-3-Clause\n  - ISC\n' > .github/dependency-review-config.yml
slopstopper run security:licences; echo "exit $?"
rm -r .github

The inventory reads scripts/requirements.txt, finds that requests is not installed in any interpreter beside it, and exits 2: a Python tree that is not installed is a tree it cannot judge, and it refuses to call that clean. pip install -r scripts/requirements.txt into a venv beside the file and run it again to see requests (Apache-2.0) judged against the four ids. The dependency review needs no such thing: it reads GitHub's own dependency graph on the pull request, which is also why it only ever runs in CI.
