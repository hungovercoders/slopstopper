Security scanning and controls for this project: what each security:* check looks at, how it blocks, and where to tune it. One file per check; this page is the map, so read only the doc whose trigger matches.

Routes

When you are…Do this
tuning what SAST blocks, or suppressing a Semgrep findingRead SAST.md for the quick start, severity table, security.sast.fail_on, the suppression pattern and this repo's suppressions
configuring or debugging the OWASP ZAP scan (baseline or OpenAPI mode), or a static host with a <meta> CSPRead DAST.md for local commands, CI wiring, risk levels, the gate (rules.tsv alert refs, CSP exceptions), the static-host alerts and api.openapi.spec
fixing a Trivy CVE finding, or when local and CI disagree on oneRead VULNERABILITY.md for the Trivy scan, the licence gate and local/CI parity (DB cache, binary version)
judging a dependency's licence, exempting one, or when the inventory says the tree is not installedRead LICENCES.md for what each ecosystem is read from, the purl exemptions, dev scope and the exit-2 cases
handling a Gitleaks finding or allowlisting a false positiveRead SECRETS.md for the quick start, the allowlist format and what to do the moment a real secret is detected
adding a third-party script, widget or any external resource to a pageRead CSP_EXCEPTIONS.md first for the strict-default + per-path exception pattern and the live list
auditing CORS, HSTS or nosniff on a JSON APIRead API_HEADERS.md for the findings, the hard-fail split, knobs and commands

Every check follows the same shape: run it locally with the task target named after it (task ss:security:sast, task ss:hygiene:csp-exceptions), read the report its page names under .ss/reports/, get a PR comment on pull requests and a GitHub issue when a blocking finding lands on main. Disable one by listing its workflow under workflows.disabled in .slopstopper.yml (or by choosing a profile that drops it). task ss:security:scan runs SAST, secrets, the dependency scan and the licence inventory in sequence.

Static Application Security Testing (SAST)

Semgrep pattern-matches your own source code for dangerous calls, injection risks and hardcoded secrets. ERROR blocks; WARNING and INFO are reported; security.sast.fail_on moves that line. Narrow, documented nosemgrep suppressions beat disabling a rule.

Dynamic Application Security Testing (DAST)

OWASP ZAP scans the running app for common web vulnerabilities. It has two modes. The baseline scan spiders an HTML site, and the API scan reads an OpenAPI spec and exercises its operations. Only the API scan finds anything on a JSON API.

Dependency Vulnerability Scanning

Trivy scans the project filesystem for known CVEs in your packages and lock files, on every PR and push and weekly against main, since a CVE lands on versions already merged. CRITICAL and HIGH block. A companion GitHub-native workflow (ss-security-vulnerability-new-check.yml) reviews newly-added dependencies on PRs and fails on a licence outside the allowlist in .github/dependency-review-config.yml. Neither gates on a devDependency advisory: Trivy scans production scope and dependency review fails on runtime scope only. That is Dependabot's job, by design; keep its alerts and security updates enabled. VULNERABILITY.md has the three-way table.

Licence Inventory

security:licences applies the same allowlist to the whole resolved tree: npm from package-lock.json, Python from pip inspect, no tool to install. A transitive package under a denied licence fails it; a licence it cannot read as SPDX is reported, never failed. LICENCES.md has the sources, the exemptions and the exit codes.

Secrets Detection

Gitleaks scans all files and full git history for credentials, tokens and private keys. Always blocking; the check never writes the credential to disk. Allowlist known false positives in the file SECRETS.md describes.

CSP Exceptions

The site ships a strict default-src 'self'; script-src 'self' Content Security Policy on every path. When a third-party widget is genuinely required on a single page (e.g. Giscus on /feedback.html), we admit it via a scoped, documented, SRI-pinned per-path exception rather than weakening the site-wide CSP. The ss:hygiene:csp-exceptions check enforces drift between worker/headers.json and the exceptions doc routed above. For adopters: this is the pattern to reuse the moment your site needs GTM, Sentry, Intercom or any analytics tag.

API Headers & CORS

On a JSON API, CORS rather than CSP decides who may read a response. security:api-headers audits that policy, plus HSTS and nosniff, and splits findings into hard failures and advisory notes.
