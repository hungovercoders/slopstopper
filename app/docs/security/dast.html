Dynamic Application Security Testing (DAST)

  1. Docs
  2. Security
  3. Dynamic Application Security Testing (DAST)

slopstopper ships automated Dynamic Application Security Testing (DAST) using OWASP ZAP to detect runtime security issues by scanning your running site. This guide explains how to customise and use the check.

Quick Start

Run Analysis Locally

# Serve the built site on :8080 as CI does, or point at a deployed URL instead
slopstopper serve &
# Run DAST scan against it
task ss:security:dast -- http://localhost:8080

What You Get Automatically

  • ✅ PR comments with DAST findings report
  • ✅ Merge blocking if any High or Medium alerts exist
  • ✅ Scheduled and post-deploy scans of the live site, with a tracking issue for blocking alerts
  • ✅ Accepted findings (documented CSP exceptions and rules.tsv entries) surfaced separately and not blocking (see below)

DAST + CSP exceptions

The DAST gate (driven by cli/slopstopper/dast_gate.py) consults docs/security/CSP_EXCEPTIONS.md on every run:

  • With no CSP_EXCEPTIONS.md file, the gate behaves exactly like a vanilla riskcode ≥ 2 cutoff, so nothing changes for you. Adopters with no third-party scripts can ignore this section entirely.
  • If you add a third-party widget (GTM, Sentry, Intercom, Giscus…), add a per-path entry to worker/headers.json for the affected path, and document it under ## Exceptions in CSP_EXCEPTIONS.md using the schema in that file. Once it's documented, ZAP's CSP findings on that exact path stop blocking the build. They still appear in the PR comment under a separate "🛡 Accepted findings" section, each naming the entry that accepted it, so they stay visible in review.
  • An exception does not unblock anything else. Any non-CSP finding (XSS, missing other headers, CSRF, etc.) on the same path still blocks, as does any finding at all on a non-documented path and any High-severity (riskcode 3) finding anywhere, including CSP High on a documented path. The exception only relaxes the Medium-CSP-on-this-path case; the rest of DAST coverage is unchanged.

The companion check ss:hygiene:csp-exceptions (workflow ss-hygiene-csp-exceptions-check.yml) keeps worker/headers.json and CSP_EXCEPTIONS.md in sync. If either side drifts, the build fails before DAST even runs.

Key Configuration Points

Change the Target URL

In Taskfile.yml, the dast task accepts the target URL as an argument:

task ss:security:dast -- http://your-site-url

In CI, pull requests and pushes to main scan a local build on http://localhost:8080. The deployed site is scanned after each successful deployment_status, daily against urls.production (skipped with a notice when unset), on a manual run given a url input, and on a Cloudflare repo after each Workers Builds deploy of main (ss-cloudflare-deployed.yml dispatches it for production only; see Deployment). Scan the deployed site when headers come from the edge (_headers, a CDN, a proxy), since a local build doesn't carry them. Every non-PR run on main opens or closes the DAST tracking issue.

Change the Blocking Threshold

Medium and High (riskcode ≥ 2) block, and that cutoff is fixed in cli/slopstopper/dast_gate.py; there is no workflow line or .slopstopper.yml knob for it. To stop a specific Medium alert blocking, scope it rather than the threshold:

  • Mark it IGNORE in .zap/rules.tsv, as a plugin id (10055, every alert that plugin raises) or an alert ref (10055-13, just that alert). Prefer the alert ref: plugin 10055 raises both "no frame-ancestors fallback" and "style-src unsafe-inline", and ignoring the plugin hides the second. The alert ref is in each alert's link at zaproxy.org/docs/alerts and in the report's alertRef field.
  • For a CSP finding caused by a third-party embed, document the path in CSP_EXCEPTIONS.md (see below).

The gate output names the entry behind every finding it swallowed.

Static hosts (GitHub Pages, S3 without CloudFront)

A host that can't send custom response headers can still enforce a CSP from a tag that comes first in every page's head:

<meta http-equiv="Content-Security-Policy"
      content="default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; object-src 'none'; base-uri 'self'; form-action 'self'">

ZAP reads it for its other CSP rules, so unsafe-inline, wildcards and missing object-src are still caught. Set form-action explicitly, because it has no fallback. A few things only a header can do, so these Medium alerts can't be fixed on such a host:

Alert refAlertWhy a meta tag can't fix it
10038-1CSP Header Not SetZAP checks for the header itself
10020-1Missing Anti-clickjacking HeaderX-Frame-Options is header-only
10055-13CSP: Failure to Define Directive with No Fallbackframe-ancestors is ignored in a meta policy

Accept exactly those, by alert ref, in .zap/rules.tsv (tab-separated, three fields):

10038-1	IGNORE	# static host: CSP is a <meta> tag, no response headers
10020-1	IGNORE	# static host: X-Frame-Options can't be set without headers
10055-13	IGNORE	# static host: frame-ancestors is ignored in a <meta> CSP

Every other CSP alert, 10055-6 (style-src unsafe-inline) included, keeps blocking. Point the CSP-exceptions drift check at the built pages with headers.format: meta and headers.source: <built HTML root>, so a page that relaxes the meta policy still has to be documented.

Disable DAST Checking

List ss-security-dast-check.yml under workflows.disabled in .slopstopper.yml and re-run install.sh, which removes the workflow and keeps it out on every refresh.

Scanning an API (ZAP OpenAPI mode)

The default scan above is ZAP's baseline, which spiders the site from the URL you pass. That is right for an HTML surface and useless against a JSON API. With no links to crawl, the scan reports next to nothing.

Point the check at an OpenAPI spec and it switches to ZAP's API scan, which reads the spec and exercises the operations it declares:

# .slopstopper.yml
api:
  openapi:
    spec: https://api.example.com/openapi.json   # URL or repo-relative file
    host_override: true                          # pass the scanned URL as ZAP's -O
task ss:security:dast -- https://api-preview.example.com
task ss:security:dast -- https://api-preview.example.com --spec openapi.yaml
BaselineAPI scan
Triggerapi.openapi.spec unsetapi.openapi.spec (or --spec) set

What it drives fromspidering a root URLthe operations in the spec
ZAP's -tthe site URLthe spec

host_override exists because a spec's servers block usually names production. Passing the scanned URL as -O points the same operations at whatever environment you are actually testing. Set it to false if your spec already names the right host.

A local spec file is staged into ZAP's mounted report directory for the run and removed afterwards, because the container only sees /zap/wrk/ and a repo-relative path can't be handed to it directly.

A scan that dies is not clean. When ZAP exits without a readable report, the check exits 2 and the markdown report says the scan did not complete, with ZAP's exit code and the last lines it wrote to stderr, so the PR comment shows the cause. In CI that fails the scan step itself, and only blocking alerts (exit 1) open the tracking issue.

Unconfigured is not failing. With no spec the check keeps its baseline behaviour, and on an api-profile repo the workflow skips rather than scanning nothing, which is the same contract as reliability:api-health and security:api-headers. So an api repo carries the DAST workflow but gets no dynamic scanning until a spec is set; that is the one step to take if you want API security coverage.

In CI, ss-security-dast-check.yml branches on the same key: with a spec it audits urls.preview on pull requests and urls.production on main and schedules; without one it keeps building the repo and serving it on localhost:8080.
