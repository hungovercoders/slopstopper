Demo recordings

  1. Docs
  2. Contributing
  3. Demo recordings

The GIF in README.md and the stills beside it are recorded from the real CLI with VHS, from the tapes under demos/, and live next to them. They are committed, so a reader never needs the tooling; a contributor re-records when what a command prints changes.

Re-recording

task contributing:demos             # every tape
task contributing:demos -- hero     # one tape

The task runs demos/render.sh, which needs vhs, ttyd 1.7.7 or newer, ffmpeg and git, plus slopstopper and task on PATH. It prefers the editable CLI in cli/.venv (what task contributing:setup creates), so a recording shows HEAD rather than a released wheel. The install tape also needs mise, because install.sh does, and a network that reaches the GitHub API, which mise uses to fetch task. It has not been recorded yet: the sandbox this pipeline was built in had neither.

Every tape runs in a scratch clone of this repo, except install.tape, which runs in an empty directory beside a slopstopper symlink to this checkout. Nothing touches the working tree, and a tape can break things (the triage tape pastes the docs map into README.md to blow its budget).

A still keeps only its last frame; render.sh lists which names are stills. The shared look lives in theme.json (the site's brand tokens as a terminal theme) and is spliced into each tape at render time, so a tape carries Set Theme @theme.json and nothing else about colour.

doctor shows the recording machine's tools, so the hero GIF is a snapshot of whoever recorded it. A machine with a tool or two missing makes the better demo, because the hints are the point.

Lesson tapes

The course under docs/learn/ has a tape per lesson, docs/learn/tapes/NN.tape, for the terminal parts of its YouTube episode. They differ from the demo tapes in four ways:

  • Generated, not written. task contributing:learn:tapes runs scripts/learntapes.py, which turns each lesson's marked blocks, in order, into the tape: one shot per block with the step's heading as a comment, clear between shots, a wait for the prompt to return after each line and a beat on each shot's output, and heredoc bodies typed fast. Edit the lesson, not the tape; -- --check reports a stale one, and the first learn shard in ci-cli.yml runs that check (with vhs validate on each tape) on every push to main and on a pull request that changes the course.
  • One size. 100 columns by 30 rows at font size 16, the episode convention in docs/learn/EPISODES.md, so every episode's terminal looks the same. The generator carries the pixel size that gives it.
  • MP4, not GIF, and not committed. task contributing:learn:record (-- 08 for one) runs render.sh with the lesson numbers, which records each tape in the scratch clone, with this checkout's node_modules linked in as the course harness does, and writes dist/learn/NN.mp4 as b-roll for the video editor. dist/ is gitignored.
  • The whole lesson, in order. A tape plays every runnable block from a clean clone, so it needs what the lesson needs: gitleaks for lesson 6, trivy for lesson 8, task contributing:setup for the browser lessons, and a CHROME_PATH for lesson 13. A block that the harness runs but vhs cannot type (a character outside printable ASCII; vhs sends keystrokes) fails the generator, which names the line.

The site's demo

app/assets/demo.svg (and its dark-theme twin demo-dark.svg), under the home-page hero, is not a tape. It is drawn by scripts/shot.py (task contributing:shots) from the real output of slopstopper checks list and slopstopper run hygiene:entry-files on this repo, as animated SVG text: no VHS, ttyd or ffmpeg, a few kilobytes, same-origin so the CSP needs nothing, and diffable in a PR. Readers who prefer reduced motion get the last screen, still. The shots job in ci-cli.yml renders it on every CLI change and uploads it as an artifact, so a change to what a command prints is seen before the committed file is re-rendered.

Adding a tape

  1. Copy the header from an existing tape (output directory, size, theme, framerate) and type only ASCII: VHS types keystrokes, so an emoji in a Type line is dropped. Emoji in the picture come from the command's output.
  2. Name it after what it shows, add it to the table above, and if it is a still add its name to stills in render.sh.
  3. Render it, look at the result, and commit the tape with its GIF or PNG. Then embed it where it earns its place; README.md sits close to its entry-files token budget, so the hero is the one GIF there.

What has bitten

  • The output directory must not exist when VHS starts. VHS moves its frames into place with a plain rename, which fails silently into a non-empty directory. render.sh removes it first and keeps VHS's temp files beside it, never inside it.
  • A long checkout path crashes Chromium. VHS puts the browser profile under its temp directory, and Chromium opens a Unix socket in it; a socket path tops out at 108 characters. Clone somewhere short.
  • Emoji one cell wide. ttyd's terminal defaults to Unicode 6 widths, so emoji overlap the next column and every table drifts. The ttyd wrapper in render.sh turns on Unicode 11; keep it when upgrading.
  • No chrome on PATH. VHS looks for chrome, google-chrome or chromium; a Playwright-installed browser is not on PATH, so a wrapper script named chromium that execs it does the job.
