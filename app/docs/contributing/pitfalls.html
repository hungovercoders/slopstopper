Common pitfalls when extending SlopStopper

  1. Docs
  2. Contributing
  3. Common pitfalls when extending SlopStopper

A short list of the most-hit gotchas. Each one has bitten somebody before; the rule is "do the obvious thing the obvious way."

Quality checks

  • Adding a quality check workflow but forgetting to add a matching Task target. CI and local diverge, so contributors can't reproduce the failure. Every workflow that runs a check must invoke task ss:<category>:<action>; the same target must exist in Taskfile.ss.yml.
  • Putting analysis output anywhere other than under .ss/reports/<category>/. It won't be .gitignored and could pollute the consumer's repo when they install SlopStopper.
  • Invoking a task without the ss: prefix. A bare hygiene:complexity gives "Task not found"; the target is task ss:hygiene:complexity, because all SlopStopper tasks live under the ss namespace via the root Taskfile.yml's includes: block. Use task ss:hygiene:complexity.

Workflows

  • Creating a new workflow file without the ss- prefix. It won't get grouped with the rest in the Actions UI, and consumers risk a clash when they install. Always name new workflows ss-<category>-<action>.yml. The single exception is copilot-setup-steps.yml, whose name is fixed by the platform.
  • Inlining npx playwright install in a workflow step. The apt phase, the time-boxed download and the browser cache live once in .github/actions/ss-playwright; a workflow that needs Chromium runs npm ci and then uses: that action with timeout-minutes on the step, because composite steps carry no timeout of their own. A shape test fails on any copy.

CSP and headers

  • Adding any external resource. CSP blocks it silently in production; test in DevTools first. If the resource is genuinely required, open a per-path exception in worker/headers.json and document it in docs/security/CSP_EXCEPTIONS.md, because the ss:hygiene:csp-exceptions check fails the build if they drift apart.
  • Adding a third-party script, form or analytics snippet without updating the privacy page. app/privacy.html and the footer line on every page state what the site collects and which services its pages reach. They are only true while that list matches worker/headers.json and the pages; a new origin, embed or form is a change to both, in the same PR, with the page's "last checked" date moved. ss:hygiene:privacy fails until the page names the new origin.

Site (app/)

  • Editing app/index.html but forgetting aria-current="page" on the active nav link. It is an accessibility regression that axe-core catches on every PR.
  • Tweaking --accent to use it as text colour. It fails AA contrast. Use --accent-deep for text on light backgrounds, --accent for decorative shapes only.
  • Adding to one HTML page's header but not the others. There is no build step or SSI, so the nav drifts. Change one, change all seven, then task contributing:learn:site and task contributing:docs:site to copy the chrome into the generated pages.
  • Linking a page to a doc on GitHub. Every reference doc is a page under app/docs/ (scripts/sitemd.py's doc_page gives the path), so a "learn more" link stays on the site. A GitHub link is for source: a workflow, a check module, a Taskfile.
  • Writing a hex colour into page CSS or an inline SVG. It stays that colour in the dark theme. Every colour is a token from app/shared.css (var(--ink) works in an SVG attribute), and the dark palette is declared twice there, so a new token goes in all three places. The accessibility audit has to pass with the OS set to dark as well as light.
