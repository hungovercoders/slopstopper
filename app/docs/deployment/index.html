How the SlopStopper site ships to production.

Overview

The site is hosted on Cloudflare. A Cloudflare Worker serves the static files in app/ via the [assets] binding and applies the per-path security headers defined in worker/headers.json. Cloudflare Workers Builds (Cloudflare's Git integration) handles the build and deploy on every push and PR, so there is no deploy workflow in this repo.

Lifecycle

EventWhat happensWhere you see it
Push to mainWorkers Builds runs npm run build, then wrangler deploy. Worker is updated; custom domain serves the new version.Commit check (Workers Builds); Cloudflare dash → Workers → slopstopper → Deployments
Open PRWorkers Builds creates a Worker version with a unique preview URL of the form <hash>-slopstopper.<account>.workers.dev.Commit check on the PR (Cloudflare Workers · Build)
New commit on the PRVersion is replaced; preview URL refreshes.Same commit check, updated.
Close PRCloudflare retires the preview version automatically.Cloudflare dash → Versions

No GitHub Action ships deploys. No NETLIFY_AUTH_TOKEN-shaped secret lives in repo settings. This is intentional, because duplicating Cloudflare's built-in capability with a GHA workflow only adds maintenance.

Configuration

FilePurpose
wrangler.jsoncWorker definition: name, compatibility date, entrypoint, [assets] binding pointing at ./app. Workers Builds reads it.
worker/index.tsThe Worker. Fetches the asset via env.ASSETS.fetch(request), then applies headers from worker/headers.json. Also redirects /feedback → /feedback.html.
worker/headers.jsonCanonical header map. Three entries: /* (strict default), /og-image.png (cross-origin CORP), /feedback.html (Giscus CSP relaxation). The Worker, slopstopper serve and the CSP-drift gate all read this.

Workers Builds runs npm run build, which is a no-op echo: the site is static HTML and CSS under app/, and Wrangler bundles worker/index.ts itself at deploy time. The asset render (task contributing:assets, which renders SVG → PNG via Playwright) runs locally before commits, and the PNG outputs are checked in.

Visibility

  • Checks after every deploy. Workers Builds reports a check run, not a GitHub deployment, so deployment_status never fires. ss-cloudflare-deployed.yml waits for that check run to succeed, then dispatches every installed URL-driven check the repo hasn't disabled (slopstopper profile disabled) on the deployed branch with the deployed URL: urls.production for main, otherwise the preview URL from the commit's row in Cloudflare's PR comment. A deploy whose branch has already moved on to a newer commit is skipped, since a dispatch runs on the branch head and its results would land on the wrong commit; the newer commit's deploy runs the checks. Results land on the commit, so they show on the PR; a run on main opens or closes each check's own issue. DAST runs against production only, because a preview answers missing paths with a bare "Not found" without the site's headers. install.sh ships it to any repo with wrangler config (at the root or one directory down, beside a site's package.json) or a worker/ directory. The per-check issues it can open gate on github.ref == 'refs/heads/main', so a provider whose deployment_status carries a SHA rather than a branch ref, or a repo whose default branch isn't main, gets the checks but not the issues.
  • Live-health README badge. The existing ss-reliability-smoke-tests.yml workflow runs hourly and after every deploy, and its GitHub Actions status badge tells you whether the live site is behaving right now.
  • Per-PR check. Cloudflare's GitHub App writes a Workers Builds check on each PR commit with the preview URL. It has the same shape as a Netlify preview deploy check.
  • Auto-issue on failure. Each URL-driven check opens (and closes) its own issue when a non-PR run on main fails against production.
  • Dashboard. Cloudflare dash → Workers → slopstopper → Deployments shows the full per-version history with build logs.

Cutover steps (manual, one-time)

  1. Confirm the Cloudflare account. Note the Account ID.
  2. Connect the repo. Cloudflare dash → Workers & Pages → Create → Connect to Git → select slopstopper. Cloudflare installs its GitHub App on the repo. Cloudflare reads wrangler.jsonc automatically; no build command override is needed.
  3. Move DNS to Cloudflare if not already there (change registrar nameservers; wait for propagation).
  4. Attach the custom domain. Cloudflare dash → Workers → slopstopper → Settings → Domains & Routes → Add Custom Domain. Cloudflare provisions the cert.
  5. (Local dev only) create an API token scoped to Account.Workers Scripts: Edit and stash it in .zshrc.local as CLOUDFLARE_API_TOKEN so wrangler dev can authenticate.
  6. Delete the Netlify site after the first successful Cloudflare prod deploy and a smoke-test pass against the new URL.
  7. Remove the NETLIFY_AUTH_TOKEN / NETLIFY_SITE_ID secrets from the GitHub repo settings.

Adopters

install.sh adds no deploy workflow. Connect your repo in the Cloudflare dash and you're done. If you prefer a different host, delete wrangler.jsonc and worker/ and wire up your own deploy. The header map in worker/headers.json is the only file the suite's CSP-drift gate cares about; everything else is optional.
