slopstopper-steward: the org-wide operator

  1. Docs
  2. Architecture
  3. slopstopper-steward: the org-wide operator

slopstopper-steward works across a GitHub organisation: it upgrades every repo that has slopstopper installed and works the issues the checks raised, one pull request each.

slopstopper is per-repo: it tells one repo what is wrong and ships how to fix it. hungovercoders/slopstopper-steward is a separate repo and package, so an adopter's install stays small and the cross-repo token stays out of every adopter.

The steward carries no check logic and no fix knowledge. Anything that explains how a check works or how to fix it belongs in the two skills here, which the steward then gets for free in every adopter.

What the steward reads from this repo

These are the surfaces its contract module names. The steward's CI checks them against this repo's main on every steward PR and nightly; nothing in this repo's own CI does, so the steward row in docs/contributing/CHANGE_MAP.md lists them for anyone changing one:

  • Discovery: the slopstopper repo topic the installer adds, the "pipx:slopstopper-cli" key in mise.toml, .ss/.installed-from.
  • Findings: the slopstopper brand label, the <!-- slopstopper:check=<name> --> and <!-- slopstopper:workflow=<file> --> body markers emit writes, and the failure tracker's workflow-failure label and ❌ Workflow Failure: <name> title.
  • Method: .claude/skills/slopstopper-triage/ and .claude/skills/slopstopper-install/ (on a big upgrade the agent works the ## Refresh-only section of its references/refresh.md), and the slopstopper-workaround: hungovercoders/slopstopper#N marker.
  • Commands: slopstopper install --no-topic, slopstopper run --json, slopstopper checks list --json, slopstopper profile expand <n> --json and slopstopper doctor --json with its needed_by (the shapes in docs/contributing/README.md).
  • Checks that need an installed environment: security:licences, registered in cli/slopstopper/checks/__init__.py, inventories the interpreter's packages (pip inspect in checks/licences.py), so the steward reports it unverified in a bare clone instead of red.
  • Releases: PyPI slopstopper-cli and the v<version> tag form (include-v-in-tag in release-please-config.json), so release notes and skills can be fetched for a pinned version.

Before merging a change to any of these, run steward contract <path to this checkout> from a steward checkout, and open the matching steward PR in the same change.

Running one for your organisation

hungovercoders/slopstopper-steward is hungovercoders' copy, not a service. Fork it (or copy it as a template), replace steward.yml from steward.yml.example with your orgs, install your own GitHub App on your adopters, add its ID as a variable and its key and an Anthropic or Claude token as secrets, and run plan-only first. Its setup runbook walks it.

What it never does

No push to a default branch, no change to repo settings, no edit of an issue, and a merge only of a PR the run itself saw green, only with merge.auto or dependabot.merge on. Every write is a steward/<order> branch and a PR carrying <!-- steward:order=<id> -->, or a fix commit on a Dependabot PR's own branch; an issue labelled steward:ignore is left alone. Its agent runs boxed inside a clone with no push rights and a dollar cap, and only for judgement calls: an open finding, or a check that went red after a refresh. Moving a pin and rewriting the suite is code.
