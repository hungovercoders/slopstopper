# Lesson 17: CI: the workflows and the PR feedback loop

**Goal.** Read one check workflow end to end, see that it is the same
`task` line you have been typing, and follow a red check from the
Actions log to the pull request comment to the issue it raises on
`main`.

## Why this lesson

The checks are the same locally and in CI by design, so the workflows
are thin: a checkout, a setup step, the one `task` line, and the
plumbing that turns its exit code into something a reviewer sees. That
plumbing is the operational loop, and it is where a suite of twenty-odd
checks either stays usable or turns into noise. Twenty-five comment
cards on every pull request is noise. One rolling comment that says
"2 of 25 failed" and folds the rest away is a signal, and a red check
on `main` that opens an issue and closes it on the next green run is a
signal nobody has to remember to look for.

This lesson is mostly reading. The runnable blocks are the greps that
prove each claim against the repository's own workflows.

## You will need

The checkout from the [syllabus](README.md). Nothing runs against a
server.

## Steps

### 1. Read one workflow

The entry-files check from lesson 3, as CI runs it. Every `ss-*.yml`
has this shape.

<!-- learn -->
```sh
sed -n '/^    steps:/,$p' .github/workflows/ss-hygiene-entry-files-check.yml | grep -E 'name:|uses:|run:'
```

```
      - name: Checkout code
        uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - name: Set up slopstopper
        uses: ./.github/actions/ss-setup
      - name: Run entry-file budget check
        run: task ss:hygiene:entry-files
      - name: Upload report
        uses: actions/upload-artifact@043fb46d1a93c77aae656e7c1c64a875d1fc6a0a # v7.0.1
      - name: Emit PR comment
        run: slopstopper emit hygiene:entry-files --target pr-comment --status ${{ steps.check.outcome == 'success' && 'pass' || 'fail' }} --on-pass=delete
```

Four things to notice:

- **The check step is the `task` line from lesson 3.** There is no
  CI-only threshold and no second implementation. `ss-setup` is a
  local composite action that installs Python and the mise-pinned
  toolchain, so the versions are the ones in `mise.toml`.
- **The report is uploaded as an artifact** before anything else is
  decided, so the file you read locally under `.ss/reports/` is the
  file a reviewer can download from the run.
- **The verdict comes from the step's exit code**, passed to the
  comment as `--status`. The emitter never parses the report to guess
  whether it passed, because `hygiene:docs-size` is advisory and its
  report can say THRESHOLDS EXCEEDED on a green run.
- **A passing check deletes its own comment** (`--on-pass=delete`), so
  a green pull request ends up with one comment, the summary.

The security checks add one step: they run `task -x`, which passes the
CLI's exit code through unchanged, so a later step can tell a finding
(1) from a check that could not run (2) and never opens an issue for
the second.

### 2. See every third-party action pinned to a commit

A tag like `@v4` can be moved to point at different code. A forty
character SHA cannot. The rule in `AGENTS.md` is that every third-party
action is pinned to one.

<!-- learn -->
```sh
grep -h "uses: " .github/workflows/ss-*.yml | grep -v "./.github/actions" | grep -v '@[0-9a-f]\{40\}' | wc -l
```

```
0
```

Zero unpinned. The local `./.github/actions/ss-setup` is excluded
because it is this repository's own code.

### 3. The one summary comment

`ss-pr-summary.yml` renders one rolling comment per pull request. It
does not run inside each check; it fires when any check workflow
completes, reads the runs GitHub has already recorded for the head
commit, and re-renders. That is why it needs no coordination with the
checks, cannot race them into a half-written comment, and converges on
the full picture whatever order they finish in.

<!-- learn -->
```sh
grep -c '"SlopStopper ·' .github/workflows/ss-pr-summary.yml
```

```
25
```

The list is explicit because `workflow_run` cannot glob, so adding a
check means adding a row here; a test in the CLI's suite fails when a
check's workflow is missing from it.

### 4. The issue a red check raises on main

A check that fails on a pull request blocks the merge. A check that
fails on `main` has nobody to block, so it opens an issue instead, and
closes it on the next green run. Two mechanisms do this:

- **The check's own emitter**, `slopstopper emit <check> --target
  issue`, opens or updates a tracking issue on a finding, and
  `--on-pass=close` closes it. It stays silent on exit 2, because a
  missing tool is not a finding.
- **The workflow-failure tracker**, which files any failed run on
  `main`, whatever the cause, so a check that could not run is still
  visible as a broken run.

<!-- learn -->
```sh
grep -n "conclusion == 'failure'" -A1 .github/workflows/ss-workflow-failure-issue.yml
```

```
48:      github.event.workflow_run.conclusion == 'failure' &&
49-      github.event.workflow_run.head_branch == 'main'
```

### 5. The rest of the loop

- **Auto-label.** `.github/labeler.yml` maps changed paths to labels, so
  a pull request touching a check's workflow, docs or module gets its
  category label without anyone choosing it. The workflow uses
  `pull_request_target` because only the base repository's token can
  label a pull request from a fork, and it runs nothing from the pull
  request's code.
- **The doc updater.** A weekly agentic workflow reads the pull requests
  merged in the last week, finds documentation that drifted, and opens
  a pull request with the fix for a human to review. Its source is a
  markdown file the gh-aw tool compiles to a lock file; you edit the
  markdown.
- **The deploy trigger.** Cloudflare Workers Builds deploys every push
  but raises no GitHub deployment, so nothing would run the URL checks
  against a preview. When Cloudflare's check run succeeds, this
  workflow works out the preview URL from the comment Cloudflare posts
  and dispatches each URL-driven check against it. Lesson 11's hourly
  smoke run against production is the same checks on a schedule.

<!-- learn -->
```sh
grep -l "cron:" .github/workflows/ss-*.yml | wc -l
grep -n "cron:" .github/workflows/ss-reliability-smoke-tests.yml
```

```
16
19:    - cron: '0 * * * *'
```

Sixteen workflows also run on a schedule, so a site that breaks between
pushes is noticed; smoke is the hourly one.

## Exercise

Find the workflow that runs the local server before its check, and the
line that starts it.

<details>
<summary>Solution</summary>

```sh
grep -l "slopstopper serve &" .github/workflows/ss-*.yml
```

The browser checks build nothing, because the site has no build step,
but on a pull request they serve `app/` on the runner and audit
`localhost:8080`, the same thing you did in lessons 11 to 15; on a
deploy or a schedule they audit the real URL instead. The API checks
never do this, because an API is not a static bundle the CLI can
serve, and guessing a start command would be worse than not guessing.

</details>
